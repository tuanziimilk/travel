## Purpose
本 skill 只负责对「单个商家 FAQ 文本版本」做 10 分制质检评分，并对 online / ai /（可选）op 给出分项分数、优劣势与可执行建议，最后对比选出最佳版本。

## Business Context（优惠券站点 FAQ 专用）
- 场景：优惠券/折扣分发站点的商家页 FAQ，不是通用客服知识库。
- 内容重点：优惠码、学生折扣、首单优惠、叠加规则、门槛、排除项、生效时间、退款后优惠处理等。
- 质量目标：
  - 用户能“看完即行动”（可执行）
  - 规则边界清晰（低投诉/低误导）
  - 本地化表达自然（适配 Country）
  - 问句可检索（有 SEO 可发现性）

## Scope / 边界（必须遵守）
- 输入：`TermID`、`TermName`、`Domain`、`Country`、`About_online`、`About_ai`、`About_op`。
- 说明：FAQ 模块沿用了历史 About 字段名；评分时将其视为 FAQ 文本版本载体。
- 输出：仅输出当前输入版本的评分 JSON，不做批量统计/看板/历史分析。
- 明确不做：直接改写为最终发布文案（只给评分和建议）。

## Inputs
推荐输入 JSON 契约：
{
  "TermID": "123",
  "TermName": "（真实商家名）",
  "Domain": "example.com",
  "Country": "US",
  "About_online": "...FAQ文本...",
  "About_ai": "...FAQ文本...",
  "About_op": ""
}

约定：
- `About_online` 与 `About_ai` 必填。
- `About_op`：`trim()` 后为空视为缺失，不评分、不出现在 `versions_present`。

## Hard Rules / 关键硬规则
1) 商家名占位规则：
   - 商家指代必须且只能使用 `{Mer.}`。
   - 输出文本（strengths/weaknesses/suggestions/key_deltas/notes）中也只允许 `{Mer.}` 指代商家。
   - `meta.Domain` 可出现域名；其他字段不得用域名/TermName 代替 `{Mer.}`。
2) 禁止第一人称：
   - 输出中不得出现 I/we/our/我/我们/咱们等。
   - 输入若出现第一人称属于扣分点。
3) 禁止编造政策事实：
   - 不得新增输入中不存在的折扣比例、具体门槛、有效期、适用/排除品类、地区规则、退款政策等。
   - 可以建议“应补充哪些信息”，但不能虚构具体值。
4) 语言与本地化判断：
   - 严格依据 `references/country-language-map.json`。
   - 只做匹配/不匹配与表达自然度判断，不引入额外国家规则。

## High-Risk Redlines（高风险红线）
以下问题即使总分接近阈值，也应在 `weaknesses` 与 `notes` 中明确标记为“高风险”：
- 叠加规则冲突：同一版本中对“可否叠加”前后矛盾。
- 生效时点缺失：未说明优惠码/折扣何时生效（结算前/结算后/活动期间）。
- 适用范围缺失（按 FAQ 类型条件触发）：
  - 当问题属于“资格/范围/限制类”（如学生折扣、叠加规则、地区限制、品类排除、订单门槛）时，若未说明关键边界，判为高风险。
  - 当问题属于“纯操作步骤类”（如入口位置、输入优惠码步骤）时，不强制要求覆盖全部范围字段，避免误伤。
- 退款相关缺失：涉及退款/取消时未说明优惠如何处理。
- 绝对化承诺：使用“永久/全部/100% 可用”等高风险表述但无条件边界。

## Advanced SEO & AI Retrieval（高级 SEO 与 AI 检索友好）
本节用于对齐“搜索引擎可发现性 + AI 问答可引用性”要求，避免仅有传统 SEO 而缺乏 AI 检索友好结构。

1) 用户意图对齐（Search Intent First）
   - 问句应覆盖高频交易型与问题型意图：
     - 折扣可用性（是否有学生折扣/首单优惠）
     - 规则边界（可否叠加、最低消费、排除品类）
     - 异常处理（优惠码不可用原因）
   - 若问句明显偏离真实意图，按 D 扣分。

2) 可抽取答案结构（Answer Extraction Friendly）
   - 答案优先“先结论、后条件、再例外”，便于片段抽取与摘要引用。
   - 避免长段无结构、模糊代词与跨句依赖过强。
   - 缺乏可抽取结构时，按 A/B/D 联合扣分。

3) 语义一致与实体稳定（Entity Consistency）
   - 核心术语前后一致：优惠码/折扣码/促销码、叠加、门槛、有效期等不得混用冲突。
   - 商家实体统一 `{Mer.}`，避免多实体指代干扰检索与引用。

4) E-E-A-T 风险控制（不编造、可验证）
   - 不写无法从输入验证的政策细节。
   - 对不确定项必须显式保留条件边界（例如“以活动页规则为准”）。
   - 任何“绝对化承诺”视为高风险。

## Output Format（必须：严格 JSON；不要 Markdown）
{
  "meta": { "TermID": "...", "Domain": "...", "Country": "...", "versions_present": ["online","ai"] 或 ["online","ai","op"] },
  "results": [
    {
      "version": "online"|"ai"|"op",
      "score_total": 0-10（1位小数）, 
      "score_breakdown": { "A":0-3, "B":0-4, "C":0-2, "D":0-1（均1位小数） },
      "strengths": ["..."],
      "weaknesses": ["..."],
      "suggestions": ["..."],
      "pass_for_publish": true/false
    }
  ],
  "comparison": {
    "best_version": "online"|"ai"|"op",
    "ranking": ["...按分数从高到低的version..."],
    "key_deltas": ["为什么最佳版本最好（2-5条）"]
  },
  "notes": "..."
}

### 输出字段硬约束
- `strengths`：3-6 条；必须可追溯到高分信号，不重复同一点。
- `weaknesses`：3-6 条；必须指出可落地问题，不重复同一点。
- `suggestions`：2-5 条；必须是可执行修改动作，不得编造事实。
- `pass_for_publish` 规则（必须严格执行）：
  - `score_total >= 8.0` 且 `A >= 2.0` 且 `B >= 3.0` 且未命中高风险红线，才为 `true`。
- 高风险封顶规则（必须严格执行）：
  - 任一版本若命中高风险红线：`pass_for_publish` 必须为 `false`。
  - 任一版本若命中高风险红线：`B <= 3.4` 且 `score_total <= 7.9`。
- SEO 满分门槛（必须严格执行）：
  - `D=1.0` 仅在“问句贴搜索意图 + 关键词自然覆盖 + 无关键词堆砌/缺失”同时满足时可给。
  - 若存在关键词覆盖不足、堆砌、问句偏离意图任一问题，`D` 最高 `0.8`。
- 并列胜负规则：
  - 总分相同：先看 `B`，再看 `A`，仍相同：`op > ai > online`。

## Scoring Rubric（必须：只用 A/B/C/D）
总分 10：
- A 结构完整与 FAQ 可读性（3.0）
- B 政策准确与可执行性（4.0）
- C 本地化与表达质量（2.0）
- D SEO 与可发现性（1.0）

评分方法：
- 先识别 FAQ 类型（避免误伤）：
  - 类型1：资格/范围/限制类（学生折扣、叠加、门槛、地区、排除项）
  - 类型2：操作步骤类（入口、填写位置、使用步骤）
  - 类型3：异常排查类（优惠码失效、未生效、订单不满足条件）
- 不同类型只对“应适用”的扣分项执行，不做一刀切。
- 从满分开始（A=3/B=4/C=2/D=1）逐条扣分。
- 扣分点必须能在 `weaknesses` 与 `suggestions` 中追溯。
- 分数保留 1 位小数。

### A（3.0）结构完整与 FAQ 可读性：扣分规则
1) 问答结构不清（问题不可检索/答非所问/绕弯）：`-0.4 / -0.8 / -1.2`
2) 核心主题覆盖不足（折扣类型/适用对象/条件/时效/售后关联缺失）：
   - 仅对资格/范围/限制类、异常排查类执行；每缺 1 类 `-0.3`，最多 `-1.5`
3) 组织混乱（信息重复、层次差、关键点埋没）：`-0.2 / -0.5 / -0.8`

### B（4.0）政策准确与可执行性：扣分规则
1) 关键条件缺失（门槛、排除项、叠加规则、适用范围、生效时点）：
   - 仅对资格/范围/限制类、异常排查类强制执行；每缺 1 类 `-0.5`，最多 `-2.0`
   - 对纯操作步骤类，不因“未覆盖全部范围字段”直接扣分，避免误伤
2) 规则模糊（“通常/可能/大多数”但无边界条件）：`-0.4 / -0.8 / -1.2`
3) 前后矛盾或可导致误导投诉：`-0.8 / -1.2 / -1.8`
4) 缺执行步骤（用户不知道下一步怎么做）：`-0.4 / -0.8 / -1.2`

### C（2.0）本地化与表达质量：扣分规则
1) 语言与 Country 不匹配：`-0.6 / -1.0`
2) 本地化术语不自然（货币/日期/配送/优惠术语）：`-0.2 / -0.5 / -0.8`
3) 模板腔、翻译腔、冗余表达：`-0.2 / -0.4 / -0.6`

### D（1.0）SEO 与可发现性：扣分规则
1) 问句不贴搜索意图（如学生折扣、优惠码不可用、可否叠加等）：`-0.2 / -0.5`
2) 关键词覆盖不足或堆砌：`-0.2 / -0.5`
3) 满分约束：存在任一 SEO 负向信号时，`D` 不得为 `1.0`（上限 `0.8`）

## Version Handling（必须）
- 必须评分 `online` 与 `ai`。
- `op` 仅在 `About_op` 非空时评分。
- `notes` 必须说明：
  - 是否缺少 `op`；
  - 语言/本地化判断依据来自 `references/country-language-map.json`；
  - 是否存在政策风险点（如叠加规则不清、时效缺失、排除项缺失）。

## Execution Checklist（内部自检；不要输出）
- 输出严格为单个 JSON 对象。
- 输出中商家指代仅 `{Mer.}`。
- 不出现第一人称。
- 分数范围正确，且 `A+B+C+D` 与 `score_total` 误差 <= 0.1。
- `comparison` 排序符合并列规则。
- `pass_for_publish` 与阈值+红线规则一致。
- 命中高风险红线时，`B` 与 `score_total` 满足封顶规则。
- `D=1.0` 时不存在 SEO 负向信号。

## Team SOP（多人长期使用建议）
1) 统一输入契约（按本文件 Inputs）。
2) 统一输出 JSON（禁止 Markdown 文本）。
3) 结果门禁校验：
   - `node scripts/score-validator.mjs --file output.json --termname "你的TermName" --strict`
4) examples 维护校验：
   - `node scripts/score-validator.mjs --lint-examples --examples assets/examples.jsonl`
